# NEOCORTEX_SPEC — Project State Layer (L3)

**Status: v1.2 — RATIFIED 2026-06-10; §7 (published trackers) ratified 2026-07-02; §8
(agent-dispatched planning output) ratified 2026-08-13; §2 (`subtype` field) ratified
2026-08-28** — companion to
`PAICodeConstitution-2026.md` Art. 6; binding per its transitional clause.
This spec itself is **L4 reference data**: amended freely via git
(Constitution layer table), no Constitutional Review needed. Supersedes the unspecified `BRAIN/` convention (2025)
**project by project**; non-migrated projects keep their `BRAIN/` until their
migration session.

**Purpose.** The NEOCORTEX is a project's continuity store: everything a
cold-start agent (or human) needs to resume work, bounded so it can actually
be read. The 2025 BRAIN failed by unbounded growth (520 KB journals, 242 KB
status files — larger than a context window) and by having no schema (17+
ad-hoc document genres across 18 projects). This spec fixes both.

**The project unit.** One NEOCORTEX per project; a *project* is the folder
that owns its own `CLAUDE.md` (or harness equivalent). Multi-module
workspaces (e.g., a parent with modules 01..09) follow ownership: a module
with its own `CLAUDE.md` gets its own NEOCORTEX; modules without one share
the parent's. The `governance/` program itself is exempt: its `PLAN_*` doc
serves as its STATUS until rollout completes, after which it gets a NEOCORTEX.

---

## 1. Directory layout

```
<project>/NEOCORTEX/
  MANIFEST.json          # mandatory — machine-readable index, archive declaration
  STATUS.md              # mandatory — bounded rebase block, OVERWRITTEN in place
  JOURNAL.md             # mandatory — current quarter only, prepend-newest
  <GENRE>_<slug>_<YYYY-MM-DD>.md   # typed documents, see §3
  _archive/              # frozen history — never deleted, always declared
```

**State vs. git (Constitution Art. 5).** Published history = any repository
with a remote. In a project whose repo has a remote, `NEOCORTEX/` is
`.gitignore`'d. A project may track its NEOCORTEX in a **local-only** repo by
explicit decision recorded in its `CLAUDE.md`. Either way, state is backed up
by local mechanisms (Time Machine, encrypted sync), never pushed.

## 2. The three mandatory files

### MANIFEST.json
Regenerated by the validator (`neocortex_manifest.py`, an L1 deliverable —
rollout plan Phase 4) whenever files are added or retired; hand-editing is
permitted but **the directory is the truth and the manifest must match it** —
on disagreement, the directory wins and the manifest is regenerated. The
validator currently runs only on demand and from the monthly fleet audit
(`governance/scripts/monthly_audit.py`); **no session-close hook invokes it**
(verified 2026-07-27 — the Stop hooks are `stop_closeout_gate.py` and
`verify_advisory.py`, neither of which calls it). Wiring it into the
session-close hook remains **pending L1 work**.
**The first entry always declares the archive** — "we know it exists."

Required fields: `spec`, `project`, `updated`, `archive{exists, span,
contents, note}`, `files[]` with `{file, genre, status, hook}` — every `.md`
in the directory except JOURNAL.md and STATUS.md must appear in `files[]`;
`genre` must be one of the six in §3. MANIFEST.json is the single sanctioned
non-markdown file in the NEOCORTEX (exhaustive exemption to the §3 data rule).

**`subtype` (optional, ratified 2026-08-28, `DECISION_drift_disposition_rulings_2026-07-29.md`
D1's open sub-point).** A file entry MAY carry a free-text `subtype` alongside its required
`genre`. The six genres (§3) are deliberately narrow and fleet-wide; `subtype` is where a
project's own local vocabulary that doesn't warrant a seventh genre lives instead of being
discarded by the rename — e.g. PROJECT-A's `PATENT`/`INVENTORY` findings, folded into the six
genres by D1, keep that distinction as `{"genre": "NOTE", "subtype": "PATENT"}` rather than
losing it. Unenforced (no fixed vocabulary, no validator change — an unrecognized extra key
was already structurally permitted; this makes the specific key sanctioned rather than merely
tolerated). Absence is not a violation — most projects will never need one.

```json
{
  "spec": "NEOCORTEX_SPEC v1.0",
  "project": "<name>",
  "updated": "YYYY-MM-DD",
  "archive": {
    "exists": true,
    "span": "2026-03 .. 2026-06",
    "contents": "pre-migration BRAIN (journal 520KB, 31 plans, 2 incidents)",
    "note": "frozen verbatim at migration; mine on demand, never delete"
  },
  "files": [
    {"file": "PLAN_x_2026-06-10.md", "genre": "PLAN", "status": "ACTIVE", "hook": "one-line summary"},
    {"file": "NOTE_patent_y_2026-06-10.md", "genre": "NOTE", "subtype": "PATENT", "status": "ACTIVE", "hook": "one-line summary"}
  ]
}
```

### STATUS.md — the bounded rebase block
- **Hard bound: 150 lines.** Overwritten in place every session — never appended.
  If it doesn't fit, it isn't status; it's history → JOURNAL.
- Required sections, in order:
  1. `## What this project is` (≤5 lines)
  2. `## Current phase` (one line + date stamp)
  3. `## Invariants` (**≤15**, numbered; cite the INCIDENT/DECISION doc that
     created each — citations may point into `_archive/`; overflow beyond 15
     is consolidated into a `PROTOCOL` doc which the list then cites)
  4. `## Next actions` (≤5, priority-ordered, each independently actionable cold)
  5. `## Pointers` (active plans, key data files, test command; the
     notification policy lives in `CLAUDE.md` only — STATUS may point to it,
     never restate it)

### JOURNAL.md — rotated, never unbounded
- Prepend-newest session entries: what was done (files, ranges, purpose),
  what remains, current state (processes, test results, blockers). Change
  rationale lives **here and in commit messages** — the 2025 in-code
  version-tag convention (`# vX.Y FIX:` comments) is retired; existing tags
  are grandfathered, never extended.
- **Rotation rule: at each quarter boundary, or upon exceeding 64 KB,**
  whichever comes first → move to `_archive/JOURNAL_<YYYY>Q<n>.md` and leave a
  ≤10-line digest at the top of the fresh JOURNAL. The size trigger is
  checked by the session-close hook (Phase 3); any agent may perform the
  rotation.

## 3. Document genres — exactly six

| Genre | Holds | 2025 genres it absorbs |
|---|---|---|
| `PLAN` | Multi-step work with task-class budgets (Art. 9) + execution log. Required for work spanning ~4+ files or shifting architecture (Art. 13). **ACTIVE plans are bounded: ≤300 lines**; overflow goes to an `_archive/` continuation noted in the plan | PLAN, SPEC, DESIGN, IMPL |
| `AUDIT` | Point-in-time evidence-based assessment, incl. verification walkthroughs | AUDIT, ANALYSIS, REVIEW, COMPARE, **WALKTHROUGH** |
| `INCIDENT` | What broke, why, and the L1/L2 rule it produced | INCIDENT |
| `DECISION` | A choice, its alternatives, and its rationale | DECISION, REFLECTION, ADVISORY |
| `NOTE` | Anything ephemeral that earns persistence | NOTE, SESSION, HANDOVER, EXPLAINER |
| `PROTOCOL` | Project-specific operating procedure or consolidated invariants | PROTOCOL, STANDARDS, CONVENTIONS |

- Naming: `GENRE_slug_YYYY-MM-DD.md`. Header line 1 carries
  `Status: ACTIVE | DONE | SUPERSEDED-BY <file> | ARCHIVED`.
- **PLAN validation gate**: when a PLAN is drafted, the drafting agent
  **proposes an adversarial review before validation, stating reasons** —
  the expected failure modes for *this* plan (omissions vs. predecessor
  artifacts, internal contradictions, unenforceable mandates, unnamed
  deliverables, lost requirements). When the plan migrates or supersedes
  prior rules, the review checks all **four loss modes**: content lost,
  scope narrowed, **timing shifted** (a "before" that became an "after"),
  and force weakened (a MUST that became a log entry) — a relocation claim
  is valid only if all four are preserved. (Both 2026-06-10 semantic losses
  were modes 2–4; the content-only review traced them as COVERED.) The user may waive the review; the
  proposal itself is mandatory. The reviewer, when run, must not be the
  drafting model (routing_policy `verifier-not-drafter`). Lesson source: the
  2026-06-10 constitution review round — 10 HIGH findings caught between
  draft and ratification, several invisible to the drafter.
- `DONE`/`SUPERSEDED` files move to `_archive/` at the next session close.
  INCIDENT docs may be archived once their lesson is encoded in L1/L2;
  STATUS invariants may cite them in `_archive/`.
- **No data in the NEOCORTEX** (MANIFEST.json excepted): any other
  non-markdown file, or anything > 64 KB, belongs in the project's `data/`
  directory (Constitution Art. 5). The validator flags violations.

## 4. Cold-start read order

`MANIFEST.json` (≈2 KB) → `STATUS.md` (≤150 lines) → ACTIVE plans (≤300
lines each). With these bounds a typical cold start costs **under 10k
tokens**; a project with several active plans may exceed it — the validator
reports the current cold-start cost so growth is visible, not silent.
JOURNAL and archives are consulted on demand, not by default.

## 5. Migration procedure (one project per session, never fleet-wide)

1. Rename `BRAIN` → `NEOCORTEX` (`git mv` only in repos where state is
   tracked per the §1 Art. 5 decision; plain `mv` otherwise) and apply the
   §1 state-vs-git rule: add `NEOCORTEX/` to `.gitignore` in any repo with a
   remote.
2. Sweep all existing files into `NEOCORTEX/_archive/` **except**: ACTIVE
   plans, INCIDENT docs still uncoded in L1/L2, and PROTOCOL docs still in
   force (rename to spec).
3. Write a fresh bounded `STATUS.md` from current reality (not from the old
   one — that's the point).
4. Start a fresh `JOURNAL.md`; the old journal goes to `_archive/` whole.
5. Generate `MANIFEST.json` (validator) with the archive declaration.
6. Update the project's `CLAUDE.md` (and any `AGENTS.md`/Antigravity rules
   file): read order = manifest → status → active plans; all `BRAIN/`
   references repointed; any `COLD_START.md` retired — its still-true content
   merges into STATUS/PROTOCOL, the file itself goes to `_archive/`.
7. Install the L1 enforcement adapter for this project: `python3 adapters/claude-code/install_adapters.py --apply` (generated local state, gitignored — idempotent, re-run anytime).
8. Evict data files (>64 KB, non-md) to `data/`.
9. Record the migration as a `NOTE_neocortex_migration_<date>.md` with a
   before/after inventory — the audit evidence (Art. 1).

## 6. What stays in the project's CLAUDE.md (not here)

Notification target, cadence, and trigger policy (single home — Art. 10);
domain safety rules; skill versions in use; environment quirks. The
NEOCORTEX holds state; CLAUDE.md holds configuration.

## 7. Published trackers — the gap this spec left open

**Status: RATIFIED 2026-07-02** (founder ruling, from the 2026-07-01 draft; amendments at ratification:
commit-message-primary cross-reference in Rule 2, implicit references made explicit — consent record in
`governance/JOURNAL.md`, 2026-07-02 entry). Lesson source: a PROJECT-A session
found two of its `docs/`-level tracking tables (a security-audit findings register, a counsel-review
register) stale — line-items the code had already closed were still shown open, because nothing links a
fix commit back to the row that describes it. §§1–6 above bind `NEOCORTEX/` (state, `.gitignore`'d,
session-close validated); they say nothing about **published trackers**: markdown tables living in a
project's tracked `docs/` (or equivalent) that enumerate discrete, closeable line-items — security
findings, counsel-review items, open bugs, migration checklists. Constitution Art. 5 draws this boundary
deliberately (state vs. publishable content) — the gap is that nothing then binds the publishable side.

**Definition.** A *published tracker* is any tracked (non-`.gitignore`'d) document containing a table or
list where each row represents one closeable item with an implicit or explicit open/closed status.

**The rule.** When a commit closes a line-item that a published tracker enumerates:
1. **Same-commit reconciliation.** The tracker's row updates (status flipped, commit/version cited) in the
   SAME commit as the fix — not a follow-up, not "later." A fix commit that closes a tracked item without
   touching the tracker is incomplete, the same way a fix without its test is incomplete (Art. 1 — evidence
   before done applies to the tracker entry too).
2. **Cross-reference tag.** The fix's commit message and the tracker's row cite the SAME finding/item ID,
   so each side finds the other (`git log --grep <ID>` / `grep <ID>` over the docs). A code-side tag
   comment is added only where the fix leaves a constraint in the code a future reader could re-break —
   PROJECT-A's existing `P1:`/`P2:`-style comments are exactly this and stay; a self-evident fix carries no
   comment, consistent with §2's retirement of in-code fix tags. (PROJECT-A's convention already did half of
   this — the missing half was the tracker never being told.)
3. **Staleness is loud, not silent.** Any published tracker over ~60 days without a touched row should be
   treated as suspect at the next `sprint_closeout` pass touching that area — not trusted blind. A tracker
   claiming "current as of `<date>`" is a claim, not a fact, until spot-checked against the code it
   describes (the exact failure mode this section exists to close: a subagent or a founder reading the
   tracker's own words instead of the live code it's describing).

**Enforcement (L1, follow-up — not yet built).** A lightweight test/lint per project that: extracts each
published tracker's item IDs, flags any row marked closed that cites no fix commit, then cross-checks the
fix-side carriers — `git log --grep <ID>` plus code-side tags where present (the `P1:`/`REV-*`/`CR-*`-style
conventions already in use) — and flags any ID found on one side but unknown to the other. Scoped as a
future L1 adapter, not drafted here; this section states the RULE the future test would enforce
(Constitution, *The Sorting Rule*: a rule earns spec prose when it can't yet be expressed as a hook — once
it can, the hook is authoritative and this prose becomes a comment).

**Not required:** retroactively fixing every historical published tracker in every project — this binds
going forward, and existing drift (like the 2026-07-01 PROJECT-A drift that sourced this section) gets
corrected opportunistically when noticed, per the existing `sprint_closeout` skill's project-pack review
step.

## 8. Agent-dispatched planning output — persisted on receipt, not from memory

**Status: RATIFIED 2026-08-13** (founder-directed, from a PROJECT-A session's own incident).
Lesson source: a PROJECT-A session dispatched a subagent to produce a full backlog+sequencing PLAN
(~262K tokens of subagent work). The orchestrating session read the returned text, extracted an
"adopted sequence for tonight" (8 of the plan's ~21 items) into `STATUS.md` and a task list, and
moved straight to execution — never calling `Write()` on the subagent's own returned text into its
own NEOCORTEX file. The un-extracted majority of the plan (the itemized remainder, plus a separate
investigation list) survived only as a one-sentence summary once the conversation later compacted;
the specifics are now unrecoverable short of re-running the dispatch. **The same project had the
correct pattern two days earlier** (`PLAN_backlog_sequencing_2026-08-10.md`, persisted and cited
repeatedly afterward) — proving the fix was already known and available, not a capability gap.

**The rule.** When an agent is dispatched (subagent, `Agent` tool, `Workflow` `agent()` call, or
equivalent) with a task whose expected output is PLAN- or DECISION-genre (§3) — a backlog,
sequencing plan, architecture proposal, or comparable multi-item planning artifact spanning more
than what the dispatching session will fully extract into STATUS/JOURNAL/a task list — **the
dispatch instruction must include: "write your own final output verbatim to
`NEOCORTEX/<GENRE>_<slug>_<date>.md` as your last action, before returning."** Persistence happens
*inside the dispatched agent's own turn*, not as a follow-up step the orchestrating session
performs (or forgets to) after reading the result. This closes the exact failure mode of the
incident above: attention shifts to "what do I execute next" the moment useful output arrives, and
a "persist it afterward" step that depends on that same attention reliably loses to it.

**Why not just tell the orchestrating session to persist it afterward, as this section's own
title might suggest.** That was tried, informally, for years of NEOCORTEX/BRAIN convention before
this section existed — the incident above shows it failing even inside a single, disciplined
session that persisted five OTHER planning docs correctly the same night. The fix has to move the
persistence step to where it cannot be skipped by a later shift in attention: the producing
agent's own final action, not the consuming session's optional next one.

**Scope note — not every agent dispatch.** A subagent doing a narrow lookup, a code edit, or a
bounded investigation whose full useful content the orchestrating session will itself write into
STATUS/JOURNAL/a commit message does not need this — the rule is for PLAN/DECISION-genre outputs
large or multi-item enough that "extract the adopted slice, discard the rest" is a real, likely
information loss, not a formality.

**Enforcement (not yet built, matching §7's own honest-limit precedent).** No hook can currently
verify that a dispatched agent's own prompt contained the persistence instruction, or that its
last action was actually a `Write()` to the right path — this is a prose rule pending its own L1
adapter, per the Constitution's Sorting Rule (a rule earns spec prose when it can't yet be
expressed as a hook; once it can, the hook is authoritative and this prose becomes a comment). The
`sprint_closeout` skill's "When drafting a PLAN" step carries the actionable half of this rule for
sessions to follow now; its step 6b (archive sweep) is the retroactive safety net that catches a
miss before a sprint closes, per that skill's own SKILL.md.
